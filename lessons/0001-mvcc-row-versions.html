Row versions: UPDATE never edits in place

15 minutes · feeds Episode 1 (pglab tables) · exit test: you can say what an UPDATE physically writes, and prove it in the lab.

The one idea

In most databases, an UPDATE edits a row where it sits. PostgreSQL does not. Every UPDATE writes a brand-new copy of the row (a new row version) and leaves the old copy behind. The old copy becomes a dead tuple — invisible to readers, but still occupying disk and memory until VACUUM removes it.

PostgreSQL trades in-place mutation for versioned history. That trade is called MVCC — Multi-Version Concurrency Control — and almost everything strange about Postgres at scale (bloat, vacuum lag, the danger of idle transactions) is a consequence of it.

This is the first claim of the Phase 1 exit test. By the end of this lesson you will have seen it with your own eyes, not read about it.

The header that makes it work: xmin and xmax

Every row version carries a small header with, among other fields, two transaction IDs:

FieldMeaning
xminID of the transaction that inserted this version
xmaxID of the transaction that deleted (or replaced) this version — 0 while none has

An UPDATE therefore does two writes: the old version gets its xmax stamped with the updating transaction, and a new version appears whose xmin is that same transaction. You can query these fields directly — they are real columns on every table:

SELECT xmin, xmax, * FROM some_table LIMIT 3;

Live vs. dead

  • A live tuple is a version that at least one possible or current snapshot can still see.
  • A dead tuple is a version that no snapshot can see anymore — but which still sits in the heap until vacuum reclaims it.

Between "live" and "dead" there is a crucial middle state that Episode 2 is about: versions that are dead in spirit but not reclaimable, because some old transaction somewhere might still want to see them. Hold that thought.

Why this trade pays off (for now)

Because nothing is edited in place, a reader never has to wait for a writer and a writer never has to wait for a reader: each just works on the versions that are visible to it. The one-line visibility rule (deep dive next lesson): a transaction sees a version if that version's xmin had committed when the transaction's snapshot was taken, and its xmax has not.

Check yourself

What does PostgreSQL physically write when you UPDATE one row?

A new full copy of the row is written and the old version is marked with the updater's xmax. Update the same row a thousand times and you have a thousand versions — this is why churn-heavy tables bloat.

In a row version's header, xmin holds…

xmin = the transaction that created this version; xmax = the one that deleted/replaced it. Visibility is decided purely by comparing these two against a snapshot.

A dead tuple is a version that…

Dead means invisible to every possible future snapshot — but still on disk. Removing dead tuples is precisely VACUUM's job, and vacuum can only do it once no live transaction might still need them.

Run it in your lab

First, write your prediction (one sentence in a scratch file): after the UPDATE below, what xmin values will the rows show — and will the xmin values you saw before the update appear anywhere?

docker exec -it pglab psql -U pglab -d pglab -c "drop table if exists t; create table t as select generate_series(1,3) AS i;"
docker exec -it pglab psql -U pglab -d pglab -c "select xmin, xmax, i from t;"
docker exec -it pglab psql -U pglab -d pglab -c "update t set i = i * 10;"
docker exec -it pglab psql -U pglab -d pglab -c "select xmin, xmax, i from t;"

Things to notice while comparing the two SELECT outputs:

  • Did any pre-update xmin value survive the UPDATE? What does that tell you about in-place vs. copy-on-write?
  • What is xmax in the second output? (Hint: these are the new versions. Where did their xmax-worthy counterpart go?)
  • The old versions didn't disappear from disk — the table just got bigger. Keep this thought; Episode 1 measures exactly this.
