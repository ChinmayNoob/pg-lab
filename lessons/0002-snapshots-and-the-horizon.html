Snapshots: who sees which version, and why an open transaction is vacuum's enemy

~15 minutes · feeds Episode 2 (pglab transactions) · exit test: you can explain why vacuum must wait for an idle session.

The one idea

A snapshot is, at its core, a list of transaction IDs that were still in progress at one instant. When a query runs, it compares each row version's xmin/xmax against that list and decides: visible, or invisible?

The rule, precisely:

A row version is visible to a snapshot if the version's xmin transaction had committed before the snapshot was taken, and its xmax transaction had not.

Note the word committed — not "started". A transaction that is open but has written nothing yet still counts as in-progress: its future writes must stay invisible, and Postgres can't know yet whether it will commit.

This explains your xmax confusion

In Lesson 0001 you observed: after the UPDATE, every row showed xmin = 752, xmax = 0 — and you honestly wrote "xmax still stays the zero, I don't know the real reason." Here is the real reason:

  • Your SELECT took a snapshot. Under that snapshot, only the new versions (xmin 752) were visible.
  • The old versions (xmin 751) did get stamped xmax = 752 — but they are invisible to your snapshot, so you can't see their headers.
  • The new versions' own xmax is 0 because nothing has replaced them yet.

One table, two generations, and every query sees only its own generation. Nothing about the header logic changed — you were simply looking at the other generation.

Why this makes vacuum wait

Now the consequence that matters for production:

A dead tuple can only be removed once no snapshot can possibly need it anymore. Any transaction still open — even one doing absolutely nothing, even one whose next query would never look at those rows — pins the horizon: vacuum must assume its snapshot could still require the old versions.

So a session that does BEGIN; SELECT 1; and then goes to lunch is not "harmless". It is a hand holding the archive door open. Every dead tuple created after its first snapshot accumulates — bloat grows, vacuum "does nothing", autovacuum keeps waking up for nothing. This is the exact failure mode from the PlanetScale article, and Episode 2's experiment will reproduce it on purpose.

One subtlety worth knowing now: the default isolation level (READ COMMITTED) takes a fresh snapshot per statement, so an idle session's next query would see new data — but its horizon is still pinned from its first statement. The danger does not require exotic isolation levels.

Check yourself

A snapshot is best described as…

The snapshot records which transactions were still running when it was taken. Visibility of each version is then decided by comparing its xmin/xmax against that list.

A row version is visible to a transaction when…

Committed is the key word — a transaction that started but hasn't committed must keep its writes invisible. And xmax committing is what makes a version invisible, not visible.

VACUUM cannot remove a dead tuple while…

The horizon rule: any open transaction's snapshot could still require the old version, so vacuum must leave it — no matter how dead it looks to everyone else.

Run it in your lab

You need two terminal windows. Terminal A will hold a transaction open; Terminal B commits an update underneath it.

First, write your prediction: after B's update commits, what will A's re-run of SELECT show — old values or new? And what changes after A finally runs COMMIT;?

# recreate the practice table (the lab was wiped for the 1M experiment)
docker exec -it pglab psql -U pglab -d pglab -c "create table t as select generate_series(1,3) as i;"
# TERMINAL A — interactive session, keep it open
docker exec -it pglab psql -U pglab -d pglab
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT xmin, xmax, i FROM t;
# TERMINAL B
docker exec -it pglab psql -U pglab -d pglab -c "update t set i = i + 100;"
# TERMINAL A again — before you run it: prediction!
SELECT xmin, xmax, i FROM t;
COMMIT;
SELECT xmin, xmax, i FROM t;

While A is still open (before its COMMIT;), run this from any window and notice who is holding the door:

docker exec -it pglab psql -U pglab -d pglab -c "select pid, state, xact_start, backend_xmin from pg_stat_activity where state = 'idle in transaction';"

Things to notice:

  • Did A see old values after B committed? Why must those old versions stay on disk?
  • What is A's backend_xmin — and what does its continued existence promise to vacuum?
  • After A commits, re-run the pg_stat_activity query: the hand on the door is gone.
